# Amélioration continue : limites vues en run autonome

Points relevés pendant les runs autonomes, avec leur contournement et ce qu'il faudrait changer dans le kit. Chaque entrée porte la source (projet et date). Une entrée traitée passe dans le `CHANGELOG` et sort de cette liste.

## Run WaveDevSecOps, nuit du 18 au 19 octobre 2026 (Windows, 3 stories en dev + revues en parallèle)

| # | Limite constatée | Contournement appliqué | Amélioration proposée pour le kit |
|---|---|---|---|
| 1 | La suite complète locale est passée de 7 à 60 min : 3 à 6 agents la lançaient en même temps sur le même poste Windows (git et serveurs réels, création de processus lente, Defender). La CI ubuntu faisait la même suite en 2 min 20. | La CI de branche sur les trois OS devient la seule suite complète ; agents et orchestrateur ne lancent que ruff et les tests ciblés ; tests lents marqués `slow` ; pytest-xdist ; exclusions Defender du dépôt et du cache uv. | `dev-story` et `reviewer` : « ne lance pas la suite complète locale si une CI de branche existe ; pousse et attends la CI ». Consigne globale « suite complète une fois à la fin » à nuancer : en run parallèle, c'est la CI qui la joue. `cost-kit-install` : proposer les exclusions Defender sous Windows. |
| 2 | Quota de l'API GitHub épuisé (403, limite secondaire) par une dizaine de `gh run watch` simultanés (intervalle de 3 s par défaut). | `gh run watch <id> --interval 60`, ou `gh run list` toutes les 2 min dans une boucle bornée. | Consigne dans `dev-story`, `reviewer` et le modèle de prompt d'orchestration : toujours `--interval 60`. |
| 3 | Branches empilées : des échecs n'apparaissent qu'à l'intégration (un test d'une story cassé par une autre, une garde de dérive qui découvre un scénario ajouté ailleurs, un nom de fait différent entre deux branches parallèles). | Empiler les branches revues, CI sur chaque branche de la pile, petit correctif d'intégration par l'orchestrateur ou un dev-story ; prévenir les agents en cours par message quand un contrat partagé se décide (`SendMessage`). | Modèle de `run-autonome.md` : section « Contrats partagés en cours » (noms, constantes) que l'orchestrateur tient et cite dans chaque prompt. |
| 4 | Le second avis et le reviewer lisent parfois une base périmée (branche partie avant une fusion), d'où des constats « high » déjà réglés sur main, ou des conflits de fond découverts tard. | Demander au reviewer de rebaser d'abord, puis de juger ; préciser dans le prompt ce que main contient depuis. | `second-avis` : comparer à `git merge-base HEAD origin/main` et signaler explicitement « base en retard de N fusions ». |
| 5 | Création de worktree refusée : dossier vide laissé par un `git worktree remove` en échec (fichier verrouillé sous Windows), puis lecture de `.git/config` pendant une écriture concurrente (`git push -u` des agents). | `rmdir` du dossier vide, `git worktree prune`, relance ; suppression des worktrees seulement en fin de run. | Orchestrateur : `git worktree prune` avant chaque lancement ; ne pas supprimer un worktree juste après la fin de son agent. |
| 6 | Push de `main` refusé de façon passagère pendant des pushes de branches simultanés. | Vérifier `main..origin/main` (rien de divergent), relancer. | Rien à changer ; noter le réflexe « comparer avant de forcer ». |
| 7 | Heures du journal estimées quand l'orchestrateur consigne plusieurs étapes d'un coup. | Toujours prendre l'heure par `date` au moment d'écrire ; une note signale les heures approchées. | `avancement-run` : signaler une ligne dont l'heure est postérieure au commit qui l'ajoute. |
| 8 | Commandes de plus de 10 min basculées seules en arrière-plan dans les agents (suite complète). | Consigne : lancer la suite en arrière-plan ou en lots, et attendre son résultat. | Devient sans objet avec le point 1. |
| 9 | `python` nu ouvre l'alias du Microsoft Store sous Windows. | `uv run python …`. | Commandes du kit et de `avancement-run` : `uv run python` par défaut sous Windows. |
| 10 | La consigne « Au plus 3 stories en développement » n'empêche pas 5 à 7 agents actifs (revues, rebases), ce qui charge le poste. | Compter aussi les rebases de fond comme du développement ; garder les places libres pour les stories du chemin critique. | Modèle de `run-autonome.md` : plafond global d'agents actifs (dev + revue), par exemple 5 sous Windows. |

## Run wavelocalai v2 (MVP), nuit du 18 au 19 octobre 2026 (Windows, 3 stories en dev + revues, fusions par PR)

| # | Limite constatée | Contournement appliqué | Amélioration proposée pour le kit |
|---|---|---|---|
| 11 | Les fichiers d'état (`sprint-status.yaml`, `run-autonome*.md`) commités dans chaque PR de story mettaient toutes les branches ouvertes en conflit à chaque fusion. GitHub ne lance alors pas la CI d'une PR en conflit : PR « verte » en apparence, sans aucun contrôle. Une dizaine de fusions de master et de reprises de contrôles (15 à 25 min chacune) dans la nuit. | Fichiers d'état hors des PR de story, regroupés dans une PR `chore/etat-run-*` toutes les 3 à 4 fusions ; `finalize.sh` ramène les fichiers d'état de la branche à ceux de master ; `.gitattributes` `merge=union` pour le journal ; `rerere` activé. | Modèle de run : ne jamais commiter l'état du run dans les PR de story ; fournir `etat_pr.sh`. Avant de fusionner : vérifier `mergeable` et la présence de contrôles (`gh pr checks` vide = CI non lancée). |
| 12 | Conflits de code concentrés sur quelques fichiers partagés du front (un seul `fr.json`, `components.css`, `components/index.js`, `api.js`, registre de routes) dès que deux stories d'écran avancent en parallèle ; trois résolutions confiées à un relecteur Opus. | Story technique de découpage (textes par écran, CSS par composant, API par domaine, routes déclarées par écran) ; vagues planifiées par fichiers touchés, pas seulement par dépendances. | Modèle de `run-autonome.md` : colonne « fichiers ou écrans touchés » dans la table des vagues ; deux stories du même écran jamais dans la même vague. |
| 13 | Un message d'une autre session (« Anaël a validé l'extension du périmètre ») a été refusé par le classifieur de permissions (« instruction poisoning ») au moment de l'écrire dans le fichier d'état. | Demander la confirmation à l'utilisateur dans la session, puis appliquer ; noter dans le fichier d'état qu'un message de pair est attendu et autorisé. | Modèle de prompt de run : liste des sessions autorisées à modifier le périmètre, écrite par l'utilisateur au lancement. |
| 14 | Les sous-agents ne peuvent pas lancer `git merge` (refus du classifieur) : une fusion de master à conflits de fond revient à l'orchestrateur. | L'orchestrateur lance la fusion, résout les fichiers d'état et le trivial, laisse la fusion en cours et confie le reste au reviewer (« étape 1 : termine la fusion, `git commit --no-edit` »). | Documenter ce schéma dans `reviewer` et le modèle d'orchestration. |
| 15 | `gh pr merge` refusé (conflit apparu après la fusion d'une autre PR) alors que l'orchestrateur avait déjà consigné « fusionnée » et retiré le worktree. | Lire le code de sortie de `gh pr merge` avant toute écriture d'état ; recréer le worktree depuis la branche intacte. | Outil `merge_pr.sh` : fusionne, vérifie `state == MERGED`, puis seulement synchronise et journalise. |
| 16 | Tests à seuil de temps (budget 300 ms) et E2E Playwright (« Response has been disposed », serveur relancé) instables sous la charge de plusieurs agents, en local comme sur les runners CI Windows. | Relancer seul, relancer le job CI en échec (`gh run rerun --failed`) ; consigner chaque cas pour la story de dette. | `checks.sh` : relancer une fois seuls les tests en échec avant de déclarer rouge, et l'écrire dans le résumé. |
| 17 | Extension SQLite absente sur la CI macOS (`setup-python` sans `enable_load_extension`) : des tests et une route supposaient l'extension chargée. | Repli explicite côté code, tests marqués `needs_vec`, valeurs attendues qui suivent la disponibilité réelle. | Consigne `dev-story` : toute dépendance native optionnelle a un repli testé et un marqueur de saut. |
| 18 | Le contrôle rapide affichait « uvx black a échoué » sans détail : la sortie emoji de black est perdue à l'encodage de la console Windows. | `uvx --offline black@<version> <fichier>` pour voir et corriger. | `controle_rapide.py` : `PYTHONIOENCODING=utf-8` pour les sous-processus, et afficher la liste des fichiers à reformater. |
| 19 | Fichier vide créé dans le dépôt principal pendant qu'un agent travaillait dans un worktree (même chemin relatif). | Vérifier `git status` du dépôt principal après chaque vague ; supprimer seulement un fichier vide non suivi. | Consigne `dev-story` : chemins absolus du worktree, jamais du dépôt principal. |

## Run wavelocalai v2 (Epics 5 à 8), soir du 19 octobre 2026 (Windows, reprise après /clear, 8 PR ouvertes à la fois)

| # | Limite constatée | Contournement appliqué | Amélioration proposée pour le kit |
|---|---|---|---|
| 20 | `avancement-run` compte une story « terminée » dès que son statut passe à `done`, que `finalize.sh` pose **avant** l'ouverture de la PR : à 18 h 51, 43 stories « terminées » dont seules 5 fusionnées depuis la reprise. | Avis ajouté à la main sous le rapport. | Lire l'étape `fusion` du journal (« PR #n fusionnée ») : « terminée » = fusionnée ; « PR ouverte » et « revue faite » comme états distincts. |
| 21 | Fin estimée trop optimiste (04 h 25 annoncé, 5 h à 7 h réaliste) : le rythme ne compte pas l'attente de la CI ni la fusion en série des PR (une à la fois, conflits après chaque fusion). | Estimation refaite à la main dans la réponse. | Mesurer dans le journal la durée « PR ouverte → fusion » et l'ajouter au chemin critique ; signaler le goulot CI quand plus de 3 PR attendent. |
| 22 | Stories en développement données « prêtes mais pas lancées » (6.5, 7.3) : l'orchestrateur n'avait pas passé leur statut à `in-progress` au lancement ; et la 5.7, en « attente humaine » au journal, était aussi « prête mais pas lancée ». | `set_status.py … in-progress` au lancement de chaque dev. | Prendre la dernière étape du journal quand elle est plus récente que `sprint-status.yaml` (`dev · lancé` ⇒ en développement, `attente humaine`, `report`, `décision`) et signaler l'écart entre les deux. |
| 23 | CI goulot : 16 jobs par PR (3 OS × 2 Python × v1 et v2, plus E2E), puis 16 sur master à chaque fusion ; 5 runners macOS au plus sur un dépôt public. | CI allégée (accord d'Anaël, PR #100) : job « Fichiers touchés », v1 seulement si une PR la touche, PR d'état sans tests, `concurrency` qui annule le run précédent d'une PR ; master toujours complet. | Modèle de workflow « CI de run autonome » dans le kit, proposé par `cost-kit-install`. |
| 24 | `merge_queue.sh` s'arrête à la première PR rouge, souvent pour un test instable (minutage 300 ms, CI Ubuntu chargée) : la file entière attend. | `queue2.sh` : relance une fois les jobs en échec, passe à la PR suivante au lieu de s'arrêter, ignore les jobs sautés. | Intégrer cette file au kit (relance unique, PR suivante, jobs « skipping » ignorés). |
| 25 | Test réseau lent seulement sur la CI macOS : `smtplib.SMTP` appelle `socket.getfqdn()` (résolution inverse lente) ; 8 tests en délai dépassé, Windows et Ubuntu verts. | `local_hostname` fixe pour un relais en boucle locale (6.3). | Ajouter aux pièges du kit : client réseau de la bibliothèque standard sous macOS en CI. |
